01

为什么先做这一块

不是跑个测试，是把「模型不可靠」这句模糊印象，量化成能查的数字。

做 LLM 应用，真正卡人的地方不是会不会调接口，而是模型输出不可靠时你怎么办。 所有号称「接了 AI」的项目，最后 80% 的工程量都花在这一点上，而大部分项目拿不出证据说自己处理过。

这一块就是把这件事摊开量一遍：固定 20 篇真实输入、判据先写死、跑两轮看失败到底长什么样。

要解决的问题只靠 prompt 会怎样代价
结构化抽取 换个输入格式就散架 输出进不了下游
失败归因 只能「再改改 prompt 试试」 不知道改哪里，成本全花在试错
校验边界 JSON.parse 通过就收下 数据错了但不报错，最难查
取舍意识 只报通过率，不讲代价 说不清成本，无法判断值不值

一句话：19/20 这个数字本身没有价值，「17 是怎么变成 19 的、剩下那 1 个为什么不修」才有价值。前者是结果，后者是过程，而过程才能被检验。

通过的代价，也得说

主动说清代价，比只报「优化到 19/20」可信得多——能讲清代价，才说明真的在权衡。

04

三条失败怎么定位

关键动作只有一个：先看 done_reason，别先改 prompt。

FAIL 1 2026-11-06-训练-01-肩+核心.md JSON 解析失败
证据
done_reason=length，输出正好 900 tok，结尾断在半句话里（2076 字符）
根因
不是模型不会，是话没说完就被掐断。9 个动作的 JSON 本身就要 900+ token，预算按平均值给必然不够
处置
预算提到 2000，同一条 930 tok 正常收尾（done_reason=stop）
FAIL 2 2026-10-24-训练-01-背+肩+腹.md JSON 解析失败
证据
done_reason=length，同样卡在 900 tok
根因
与 FAIL 1 完全相同。两条失败一个原因，这也是为什么不能一条条改 prompt
处置
同上，1155 tok 收尾
FAIL 3 2026-10-22-训练-01-腿A（股四主导）+腹.md session: Required
证据
done_reason=stop——话说完了，但顶层键变成了 trainingSession / workoutPlan / HRV / notes
根因
prompt 缺 session 取值规则。正文里有「本次训练计划为恢复性训练」这类计划文本，模型被带跑，把 session 吞进 notes 里，自己另起了一套字段名
处置
prompt 补一条：优先取 frontmatter，其次取一级标题，并明确写出“计划说明不是 session 名”；同时禁止新增字段。重跑仍失败，见第 06 节

这一步的方法论，比结论重要

三条失败看起来都是「输出不对」，但只有分开看 done_reason 才知道是两类问题： 被截断（length）和跑偏（stop 但内容错）。前者是参数问题，后者是 prompt 问题， 修法完全不同。如果三条一起当「模型不行」处理，会去加 few-shot、换模型、上更复杂的 prompt——全是白费。

先分类，再动手。三个失败样本、两个根因、两个动作。这句话在任何一次线上排障里都成立。

05

改了什么

两处，都在 src/lib/extract.ts。注释写清了为什么，防止以后被改回去。

改动一 · token 预算 
// 输出 token 预算。不要再调回 900。
// 900 时 2/20 被截断（done_reason=length，输出正好 900 tok），
// 放到 2000 后同样两条 930 / 1155 tok 正常收尾。
// 9 个动作的 JSON 就要 900+ tok，游泳只要 60 tok ——
// 按最坏情况给预算，代价只是截断概率归零，不会让短记录变慢。
- export const NUM_PREDICT = 900;
+ export const NUM_PREDICT = 2000;
改动二 · prompt 补 session 规则 
+ session 怎么取（必填，不许省）：
+ - 优先取 frontmatter 的 session 字段原值
+ - 没有就取一级标题「# YYYY-MM-DD 训练 · XXX」里的 XXX
+ - 正文里的计划说明、教练备注、恢复性训练这类文字
+   不是 session 名，不要拿它当 session
+
+ 不许新增结构里没有的字段（不是 notes、不是 summary）。

第二条里那句「不是 session 名」是这次唯一带对抗性的写法。 光说「从 frontmatter 取」不够——得同时告诉它什么不许当，否则模型会从正文里挑一个看起来最像标题的短语顶上。

06

剩下的那 1 条

它没被修掉，但它证明了整个方案里最要紧的一件事。

10-22 那篇有 14 个动作，是全部样本里最长的一条。补完 prompt 重跑，它依然失败。 把原始输出打出来看，模型的顶层键是这样的：

date trainingSession workoutPlan HRV restingHeartRate sleepQuality trainingLoad previousLoad previousLoadHistory notes

它整篇放弃了 schema，自己发明了一套——连 date 都编成了 2023-10-23， 而记录明明是 2026 年的。这不是「少个字段」，是指在长输入下失去了对齐。

为什么这条不能算 pass

如果只做 JSON.parse 不做 Zod，这个输出会被当成合规收下： 语法完全合法，解析不报错，字段名还挺像那么回事。然后你会得到一条 2023 年的训练记录，混进数据库，几周后没人知道数据为什么不对。

「能解析」不等于「抽对了」。Zod 是这次唯一拦住它的东西。这也正好是「模型不许改数字」那句原则的实证——不是理论，是拦下来过一次。

为什么不现在修

修法至少有三个：① 只喂 frontmatter + 动作明细，不喂计划和点评段落；② 按 5 个动作分块抽再合并；③ 加 few-shot 反例。 这三个改法各有代价，而现在数据不够判断该选哪个——20 条样本里只有 1 条长记录失败，样本量撑不起结论。 下一步该做的是量化「输入长度」和「跑偏概率」的关系，而不是先猜一个改法。

07

关键概念

五个概念，每个附一个问题——能答上来，说明这一段没白跑。

01

约束解码 / JSON mode

模型生成每个 token 时，其实是在词表上算概率分布。JSON mode 的做法是把不符合 JSON 语法的 token 概率压成 0，让它物理上只能吐出合法 JSON。所以它保证的是「语法」，不是「语义」——这正是第 06 节那条失败的原因。

自检　JSON mode 开着，模型还有可能输出不合规的内容吗？可能的话，长什么样？
02

Zod 与「运行时类型」

TypeScript 的类型在编译后全部消失，运行时一个都不剩。所以 as TrainingRecord 是纯谎言——它不检查任何东西，只是让编译器闭嘴。Zod 是同一份约束的运行时版本：safeParse 不抛异常，返回 {success, data | error}，正好适合接口边界。

自检　JSON.parse(x) as Foo 和 FooSchema.parse(JSON.parse(x))，哪个会在数据错的时候报警？为什么？
03

token 预算与 done_reason

num_predict 是输出上限（不是目标值）。模型生成到自然结束会返回 done_reason=stop；撞到上限被掐断则是 length。这是判断「截断」还是「跑偏」的唯一可靠信号，比看输出内容猜要准得多。

自检　一条输出 JSON 解析失败，你怎么在 10 秒内判断是预算不够还是模型跑偏？
04

为什么失败要分类，不能笼统算「准确率」

「合规率 85%」这个数字没有指导意义——它不告诉你下一步该改什么。而「2 条截断 + 1 条跑偏」直接指向两个不同的动作。指标的价值在于能否驱动决策，不在于是否漂亮。这也是为什么测试脚本要同时报「语法合规」和「字段一致」两个数：它们失败时的修法不同。

自检　如果只报一个「19/20」，你会漏掉什么信息？
05

单一出处原则（single source of truth）

prompt 和校验逻辑各只留一份，HTTP 接口和测试脚本都 import 它。原因不是「代码好看」，而是两份实现必然漂移：你改了接口那份忘了改测试那份，测试就会一直绿着，而线上已经错了。这类错误在上一轮真发生过。

自检　如果 route.ts 里单独写了一份 prompt，一周后可能出现什么状况？
08

下一步

判据已过，但还有一处未解决。下一步不是马上改，而是先拿到数据。

  1. 量一遍输入长度　把这 20 篇的字符数、动作数打出来，看 10-22 那篇是不是真的明显最长。如果它只是略长，说明锅不在长度。
  2. 把三条失败各重跑 3 次　同一个输入跑 3 次结果一样吗？temperature=0 下如果还不稳定，说明是模型容量问题，不是随机性。
  3. 先写结论，不急着写代码　一句话：14 个动作的长记录该走分块、还是砍输入、还是加反例。结论先记下来，改法等数据。
  4. 补一次 HTTP 层的验证　在本地手动起服务，curl 一次 /api/extract，确认 route 和脚本行为一致。

一处已知限制

本轮的 20 次测试是直接请求 Ollama的：prompt 与 Zod 校验都取自 src/lib/extract.ts，和 route 用的是同一份， 所以验的是同一件事，但 HTTP 那一层没有被覆盖。这条单独补。
