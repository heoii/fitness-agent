# fitness-agent

从个人训练记录里抽取结构化数据的 Agent 项目。目标不是"做个健身 App"，是把 LLM 应用的工程链路跑通：
结构化输出 → 检索 → 流式 → 控制循环 → 评测。

**实测报告（可直接看）：https://heoii.github.io/fitness-agent/**

---

| ③ 切片与召回 | md 按标题层级切片 → 向量入库 → 召回 ≥70% | **已测完，结论是向量没赢**（W3–W5，11-15）：804 篇 → 3045 chunk（入库 3029）；15 题 × 6 方案，**BM25·标题切 Sec@5 100%、向量 93%**。目标线 70% 两条都过，但多花 63 MB 和 76 秒换不来更好，原因见报告与下文 |

评测口径（2026-11-15 起）：**只统计力量记录**。cardio（游泳/步行）结构极简、输出 60 tok 就够，
天然合规，放在分母里属于送分 —— 早先的「19/20」有近一半是这种样本。现在 20 篇全是力量记录，
每一篇都要过「按 `###` 分动作、按组读重量」这一关。

## 它是怎么工作的

```
训练记录 md
  → 输入清洗（只留「动作明细 / 训练摘要」段，切掉复盘、下次计划）
  → prompt（字段口径固定，禁止新增/改名）
  → qwen2.5:7b-instruct（temperature=0, format=json）
  → 闸一 JSON.parse      能不能读
  → 闸二 Zod             字段对不对
  → 闸三 字段比对         内容对不对（测试脚本独有）
  → ok / 兜底（永不 500）
```

## 命令

**结构化输出（W2，要跑模型）**

```bash
npm run dev        # 开发服务器
npm run test:5     # 冒烟测试（5 篇力量记录，约 3 分钟）
npm run test:20    # 完整测试（20 篇力量记录，约 15 分钟）
npm run profile    # 只看输入规模，不跑模型（1 秒）
```

**语料 / 切片 / 结构抽取（W3，不调模型，秒级）**

```bash
npm run w3:stats   # 遍历 804 篇 → 条目数 + type/年份分布 + 5 条判据（含递归自洽）
npm run w3:chunk   # 切 3045 个 chunk + 4 条层级判据
npm run w3:parse   # 抽 1214 个动作 + 3 条抽取判据（含容量交叉校验）

# 单篇细看
npx tsx scripts/chunk_dump.ts --doc 2026-11-07-训练-01-腿A        # chunk 树
npx tsx scripts/parse_training.ts --doc 2026-11-07-训练-01-腿A    # 逐组打印
npx tsx scripts/parse_training.ts --json 2026-11-07-训练-01-腿A   # 原始 JSON
```

**向量入库（W4，需要 Ollama + `bge-m3`）**

```bash
ollama pull bge-m3          # 1.2 GB，1024 维；首次要下
npm run w4:embed           # 100 条 → private/embeddings/sample100.json + 3 条判据
npm run w4:embed -- --query "深蹲 掉力"   # 换问题看 top5（可重复传）
npm run w4:embed -- --force              # 语料变了之后重算（默认复用，不重嵌入）
```

**检索评测（W5，需要 Ollama + `bge-m3`）**

```bash
npm run w5:index                        # 全量 3029 chunk → private/embeddings/full.json（约 76s）
npm run w5:eval -- --verify             # 只查标注：15 题的答案是否真能在库里定位（不跑分）
npm run w5:eval                         # 6 种方案 × 15 题，输出 Doc@k / Sec@k / MRR
npm run w5:eval -- --explain S8         # 单题归因：四个方案的 top5 各是什么
npm run w5:eval -- --no-fixed --no-h2   # 只跑标题切那一行（省两次嵌入）
npm run w5:qa                           # 6 道数值题的独立入口（不走向量）
```

`--verify` 不是可有可无的开关。第一次跑它就抓出 4 道标准答案**指向不存在的文件**的题——
如果先跑分后核对，结果是「所有方案一起掉到 73%」，然后你会去查模型和参数，而真正的问题是答案标错了。

向量文件**只落 `private/`**（已 gitignore，且 `git_sync.py` 有一道闸）：chunk 正文是真实训练记录，
这个仓是公开的。

需要本机跑着 Ollama 并已拉取 `qwen2.5:7b-instruct`（只有 W2 那几个命令需要）：

```bash
ollama list                       # 确认模型在
ollama serve                      # 没在跑就起一下
```

## 失败过什么（三轮）

20 篇力量记录现在 20/20。这个数字之前的每一步都是被真实失败推着走的，不是一次写对的：

| 轮次 | 结果 | 真实原因 | 改法 |
|---|---|---|---|
| 11-14 第一轮 | 17/20 | 输出预算 900 tok 截断 ×2；prompt 没给 session 取法 | 预算提到 2000；prompt 补 session 规则 |
| 11-14 第二轮 | 19/20 | `2026-10-22` 同篇里有「教练复盘」+「下次处方表」，模型把处方当成训练记录 | 输入侧只喂记录段（`trimToRecord`） |
| 11-15 第三轮 | 20/20 | 同一篇里同名动作出现两次，模型合并后补了一个 `reps: null` 空组 | prompt 加「同名动作各算一个，不许补空组」 |

第三轮还顺手修了一处校准错误：模型对可省字段给 `null` 而非省略，schema 只认省略，于是整条被判不合规。
`null` 与缺失同义 → 归一化成 `undefined`，但类型错（字符串、负数）照旧拦。

## 切片为什么不按字数切（W3）

语料的语义边界就是标题：`## 动作明细` 下是一组动作、`## 摘要` 是一句话结论。按固定字数切
（512 token 滑窗那套）会把「1RM 的定义」切成上一块结尾 + 下一块开头，检索命中一个也读不懂。

所以切两层：主边界 `##`；若该段里还有 `###` 就继续细到叶子，但 `headingPath` 保留完整父级
（`动作明细 > 史密斯深蹲（kg）— 容量 2060`）。训练记录的 `## 动作明细` 有 8 个动作、700 多字，
整段做成一个 chunk 语义太杂——问「深蹲掉力」会命中整段，前 5 条近邻全是同一篇的其他动作。

过短块（`## 摘要` 那种一句话）**不在切片阶段合并**：合并属于检索调优，W5 看 recall 再定。
切片只负责不丢内容、可回溯。

## 两个「看起来没坏」的错（W3/W4）

这两个都不是崩溃，都是**结果看着正常、结论全错**，所以单独记一节：

**① CRLF 让 235 篇的标题全部失效。** 语料里 235/989 篇是 Windows 写的 CRLF。`split("\n")` 之后
行尾还挂着 `\r`，而标题正则的 `(.*)$` 里 `.` 不匹配 `\r`、`$` 又只认整串结尾 —— 于是**每一个标题
都匹配不上**，整篇塌成一个无标题大块，`headingPath` 变空，检索时引用不到任何小节。

它能活到 W4 才被发现，是因为 W3 那条判据**自指**：「headingPath 每级都出现在本文档标题行里」——
用它自己的同一个正则去核对，两边同时失败就互相印证成「通过」。现在的改法两层：`loadDoc` 统一
换行符（单一出处，下游不用各自防），判据加一条独立的「有标题的文档不许切出空路径块」。
修完 chunk 数 2624 → 3045、超长硬切 148 → 40。

**② 取样偏差让样本里根本没有答案。** W4 第一版按文档轮转取 100 条，结果 98/100 都是文档标题块——
训练记录的第一块永远是标题块，`## 动作明细` 那种带动作数据的块一条进不来。表现是问「深蹲掉力」
返回一堆「引体专项」标题块：**分数正常、排序单调、top5 都有内容，就是没答案**。

改法是每篇按序号旋转起点，并且在输出里打印结构分布（现在 动作明细 66 / 标题块 28 / 摘要 6）。
道理很朴素：**取样之后要看一眼「取到了什么」，而不是只看「取到几条」。**

## W5：向量没赢过 BM25（2026-11-15）

建了全量索引（3029 chunk × 1024 维，63.6 MB，76 秒），然后拿 15 道题、6 种方案去测它值不值得留。
**结果是我原来的假设错了：向量在三组切法下全部输给 BM25。**

| 方案 | Doc@1 | Doc@5 | Sec@1 | Sec@5 | MRR |
|---|---|---|---|---|---|
| **BM25 · 标题切** | **87%** | **100%** | **80%** | **100%** | **0.880** |
| 向量 · 标题切 | 73% | 93% | 73% | 93% | 0.843 |
| BM25 · H2 级 | 87% | 100% | 80% | 93% | 0.862 |
| 向量 · H2 级 | 60% | 87% | 60% | 87% | 0.711 |
| BM25 · 固定切 | 87% | 93% | 53% | 73% | 0.613 |
| 向量 · 固定切 | 47% | 80% | 27% | 73% | 0.480 |

三条可以直接读出来的：

1. **BM25 的 Doc@1 恒定 87%，完全不随切法变化；向量在 47%–73% 之间大幅波动。**
   BM25 对切法鲁棒，向量对切法敏感 —— 这比「谁赢」更有信息量。
2. **标题上下文对两边都关键，但对向量是生死线。** 固定切（无标题）时向量 Doc@1 只有 47%。
3. **向量唯一明显赢的一题是术语不一致**：题面「心率变异性」、语料 0 篇用这个词（223 篇用「HRV」），
   向量排第 1、BM25 排第 10。这是它真正的位置——不是普遍更强，而是**处理词表不重合**。

### 但「BM25 100%」这个数字要打折看

写题的时候我是看着语料写的，题面里的词和语料里的词是同一批。查了一遍：8 道「语义题」里
**只有 1 道是真正的跨术语题**（S3），其余 7 道都是同词匹配。这属于**出题者偏差**，
真实用户不会先读语料再提问（他会说「那个蹬腿的机器」）。

试过补一组纯口语题，做不下去——语料高度同质，任何不含日期、不含动作名的描述都能对上十几篇文档，
**ground truth 无法唯一**。这个失败本身也是结论：这份语料上语义检索的价值上限本来就低。

所以**暂时不换 BM25，也不删向量**，先做两件事再决定：把论述性语料（计划文档、知识笔记）进库，
以及补 10 道真·跨术语题。如果那时 BM25 还是赢，就痛快换掉。

细节、逐题排名、归因、五条「不能下的结论」：https://heoii.github.io/fitness-agent/retrieval.html

## 三个设计取舍

1. **单一出处**：prompt、输入清洗、校验只在 `src/lib/extract.ts` 写一份，接口和测试都 import 它。
   两份实现必然漂移，改了接口那份忘了测试那份，测试会一直绿着而线上已错。
2. **按最坏情况给 token 预算**（2000 而非 900）：代价是延迟上升，换来截断概率归零。
   短记录不受影响——预算是上限不是固定开销。
3. **失败不抛异常**：返回 `{ok:false, raw, issues}`。接口永远不 500，调用方永远拿得到能处理的东西。

## 还没做

- **HTTP 层未实测**：完整测试直接请求 Ollama，`/api/extract` 那条 route 还没 curl 过（本机沙箱起不了 dev server）。
- **只覆盖力量记录**：cardio 的 schema 分支还在（真喂游泳文本不会崩），但不在评测范围内。
- **只有 20 篇**：样本量够说明稳定性，不够说明分布外泛化。213 篇力量记录里还有 193 篇没进过评测。
- **还没接进查询链路**：3029 个块的索引只活在评测脚本里，App 侧一次都没调用过。
  所以「用 BM25 还是向量」目前还是个纸面问题，真实延迟与成本要等接进去才看得见。
- **W5 之后的五件事**（按「能改变结论」排序，详见报告第 10 节）：
  1. **论述性语料进库**：现在只测了「每日记录」，知识库里的计划文档、知识笔记、复盘都没进。
     那些才是向量该赢的地方，结论的适用范围被语料限死了。
  2. **补 10 道真·跨术语题**：像 S3 那样，题面用中文全称、语料用英文缩写（或反之）。
     现在只有 1 道，不足以下「向量在术语不一致时更好」这个判断。
  3. **混合检索**：BM25 与向量各有胜场，RRF 融合至少不会比 BM25 差。
  4. **小块合并实验**：S8 那题向量排第 7，原因是答案被切成几个短块、语义不完整。
  5. **人工相关性分级**：现在判据是二值的（命中那节算对），缺「部分相关」这一档。
- **两个 W3 遗留的口径**（已确认，不是 bug）：
  - **容量字段不能当基准**：1214 个动作里 41 个对不上，其中 34 个是引体向上——练练对自重动作按体重折算、对双侧动作算两侧。这是 App 的算法，不是解析错；但意味着「容量」只能在同动作内比较，不能跨动作求和。
  - **2 篇源数据的「动作明细」段本身是空的**（2025-08-11 拳击、2025-09-11 训练），抽取正确返回 0 个动作，不是 bug。
- **硬切点不会切在句中**：40 个超长块（21 个续块）都按行累加后切，切点必然落在行首，不是滑窗那种半个句子——
  所以 `maxChars=1200` 暂不调整。真正的问题在别处：续块与首块共用同一个 `headingPath`，
  检索命中续块时看不出它是后半段。**这一点 W5 没有专门验证**（45 个续块里没有一道题打中它们），仍是待办。
