# fitness-agent

从个人训练记录里抽取结构化数据的 Agent 项目。目标不是"做个健身 App"，是把 LLM 应用的工程链路跑通：
结构化输出 → 检索 → 流式 → 控制循环 → 评测。

**实测报告（可直接看）：https://heoii.github.io/fitness-agent/**

每一篇都要过「按 `###` 分动作、按组读重量」这一关。

## 它是怎么工作的

两条链路，共用一个模型和一份 prompt 出处。

```
① 抽取（W2）
训练记录 md
  → 输入清洗（只留「动作明细 / 训练摘要」段，切掉复盘、下次计划）
  → prompt（字段口径固定，禁止新增/改名）
  → qwen2.5:7b-instruct（temperature=0, format=json）
  → 闸一 JSON.parse      能不能读
  → 闸二 Zod             字段对不对
  → 闸三 字段比对         内容对不对（测试脚本独有）
  → ok / 兜底（永不 500）

② 问答（W6）
问题（用户原话）
  → 查询清洗（剥掉「最近 / 还是 / 为什么」这类词）   ← 为什么必须剥：「最近」在
                                                     这个语料里 DF 极低 → IDF 比「深蹲」还高
  → BM25 取 top50
  → 时间重排  score × (0.55 + 0.45 × 时间因子)      ← 用户说「最近」时半衰期 45 天
  → top5 组装成 [1]..[5]
  → qwen2.5:7b-instruct（明令禁止自己算数）
  → 引用校验：答案里的 [n] 必须都 ≤ 5，越界就是编引用
  → 答不出 → 「资料里没有找到」，不编
```

```bash
npm run dev        # 开发服务器
npm run test:5     # 冒烟测试（5 篇力量记录，约 3 分钟）
npm run test:20    # 完整测试（20 篇力量记录，约 15 分钟）
npm run profile    # 只看输入规模，不跑模型（1 秒）
```

**语料 / 切片 / 结构抽取（W3，不调模型，秒级）**

```bash
npm run w3:stats   # 遍历 804 篇 → 条目数 + type/年份分布 + 5 条判据（含递归自洽）
npm run w3:chunk   # 切 3045 个 chunk + 4 条层级判据
npm run w3:parse   # 抽 1214 个动作 + 3 条抽取判据（含容量交叉校验）

# 单篇细看
npx tsx scripts/chunk_dump.ts --doc 2026-11-07-训练-01-腿A        # chunk 树
npx tsx scripts/parse_training.ts --doc 2026-11-07-训练-01-腿A    # 逐组打印
npx tsx scripts/parse_training.ts --json 2026-11-07-训练-01-腿A   # 原始 JSON
```

**向量入库（W4，需要 Ollama + `bge-m3`）**

```bash
ollama pull bge-m3          # 1.2 GB，1024 维；首次要下
npm run w4:embed           # 100 条 → private/embeddings/sample100.json + 3 条判据
npm run w4:embed -- --query "深蹲 掉力"   # 换问题看 top5（可重复传）
npm run w4:embed -- --force              # 语料变了之后重算（默认复用，不重嵌入）
```

**检索评测（W5，需要 Ollama + `bge-m3`）**

```bash
npm run w5:index                        # 全量 3029 chunk → private/embeddings/full.json（约 76s）
npm run w5:eval -- --verify             # 只查标注：15 题的答案是否真能在库里定位（不跑分）
npm run w5:eval                         # 6 种方案 × 15 题，输出 Doc@k / Sec@k / MRR
npm run w5:eval -- --explain S8         # 单题归因：四个方案的 top5 各是什么
npm run w5:eval -- --no-fixed --no-h2   # 只跑标题切那一行（省两次嵌入）
npm run w5:qa                           # 6 道数值题的独立入口（不走向量）
```

`--verify` 不是可有可无的开关。第一次跑它就抓出 4 道标准答案**指向不存在的文件**的题——
如果先跑分后核对，结果是「所有方案一起掉到 73%」，然后你会去查模型和参数，而真正的问题是答案标错了。

向量文件**只落 `private/`**（已 gitignore，且 `git_sync.py` 有一道闸）：chunk 正文是真实训练记录，
这个仓是公开的。

**问答链路（W6，要跑模型）**

```bash
npm run dev                                    # localhost:3000 就是问答页；也支持 /?q=问题
npm run w6:ask                                 # 25 题验收：引用合法 / 可定位 / 承认没找到 / 算数走工具 + 分类准确率
npm run w6:ask -- --only=C                     # 只跑需要算数的那组（改 prompt 时用，全量要 1.5 分钟）
npm run w6:debug -- --q "深蹲最近在涨还是在跌"   # 基线与产品各排一遍，看该命中的排第几
npm run w6:debug -- --q "史密斯深蹲 容量" --expect 2026-11-07 2026-11-14
npm run w6:latency                             # 三段延迟：冷启动 / 加载索引 / 单次查询
npm run w6:llm                                 # 本地 7B 能力边界：拒答 / 表述 / 算数（冷热分离）
```

**数值入口（W7，不调模型，秒级）**

```bash
npm run w7:trend                                # 趋势工具：双口径 + 降级课 + 歧义候选
npm run w7:trend -- 腿举(倒蹬)                  # 换动作看
npm run w7:count                                # 计数工具：次数对人工核过的真值
npm run w7:scope                                # 语料范围实验：只索引每日记录 vs 整个知识库
npm run w7:latest                               # 定位工具：最近一次是那天，对不对
npm run w7:multi                                # 多实体展开：一个问题里有几个对象，是不是都答了
npm run w7:entity                               # 实体识别：并列问句切出来的对象对不对
npm run w7:agg                                  # 聚合与对比：区间边界、每周频率的分母
npm run w7:stale                                # 荒废：每个动作的最晚日期，按天数排序
npm run w7:stream                               # 流式与取消：事件顺序 / token 拼接 / 取消耗时
```

`w7:count` 的判据表里写的是**人工 grep 语料核对过的数字**（2026-11 腿课 = 11-07、11-14 两节），
不是工具输出的回抄。抄工具的输出去做判据，工具算错时判据会一起错——那等于没判。

`w6:debug` 的价值在 `--expect`：它把「检索有没有找到它该找的东西」变成一个可断言的数字，
而不是靠人翻 top5 猜。改成产品检索器时就是靠它确认 11-07 从 #49 掉到了 #3。

需要本机跑着 Ollama 并已拉取 `qwen2.5:7b-instruct`（只有 W2 那几个命令需要）：

```bash
ollama list                       # 确认模型在
ollama serve                      # 没在跑就起一下
```

## 失败过什么（三轮）

20 篇力量记录现在 20/20。这个数字之前的每一步都是被真实失败推着走的，不是一次写对的：

| 轮次 | 结果 | 真实原因 | 改法 |
|---|---|---|---|
| 11-14 第一轮 | 17/20 | 输出预算 900 tok 截断 ×2；prompt 没给 session 取法 | 预算提到 2000；prompt 补 session 规则 |
| 11-14 第二轮 | 19/20 | `2026-10-22` 同篇里有「教练复盘」+「下次处方表」，模型把处方当成训练记录 | 输入侧只喂记录段（`trimToRecord`） |
| 11-15 第三轮 | 20/20 | 同一篇里同名动作出现两次，模型合并后补了一个 `reps: null` 空组 | prompt 加「同名动作各算一个，不许补空组」 |

第三轮还顺手修了一处校准错误：模型对可省字段给 `null` 而非省略，schema 只认省略，于是整条被判不合规。
`null` 与缺失同义 → 归一化成 `undefined`，但类型错（字符串、负数）照旧拦。

## 切片为什么不按字数切（W3）

语料的语义边界就是标题：`## 动作明细` 下是一组动作、`## 摘要` 是一句话结论。按固定字数切
（512 token 滑窗那套）会把「1RM 的定义」切成上一块结尾 + 下一块开头，检索命中一个也读不懂。

所以切两层：主边界 `##`；若该段里还有 `###` 就继续细到叶子，但 `headingPath` 保留完整父级
（`动作明细 > 史密斯深蹲（kg）— 容量 2060`）。训练记录的 `## 动作明细` 有 8 个动作、700 多字，
整段做成一个 chunk 语义太杂——问「深蹲掉力」会命中整段，前 5 条近邻全是同一篇的其他动作。

过短块（`## 摘要` 那种一句话）**不在切片阶段合并**：合并属于检索调优，W5 看 recall 再定。
切片只负责不丢内容、可回溯。

## 两个「看起来没坏」的错（W3/W4）

这两个都不是崩溃，都是**结果看着正常、结论全错**，所以单独记一节：

**① CRLF 让 235 篇的标题全部失效。** 语料里 235/989 篇是 Windows 写的 CRLF。`split("\n")` 之后
行尾还挂着 `\r`，而标题正则的 `(.*)$` 里 `.` 不匹配 `\r`、`$` 又只认整串结尾 —— 于是**每一个标题
都匹配不上**，整篇塌成一个无标题大块，`headingPath` 变空，检索时引用不到任何小节。

它能活到 W4 才被发现，是因为 W3 那条判据**自指**：「headingPath 每级都出现在本文档标题行里」——
用它自己的同一个正则去核对，两边同时失败就互相印证成「通过」。现在的改法两层：`loadDoc` 统一
换行符（单一出处，下游不用各自防），判据加一条独立的「有标题的文档不许切出空路径块」。
修完 chunk 数 2624 → 3045、超长硬切 148 → 40。

**② 取样偏差让样本里根本没有答案。** W4 第一版按文档轮转取 100 条，结果 98/100 都是文档标题块——
训练记录的第一块永远是标题块，`## 动作明细` 那种带动作数据的块一条进不来。表现是问「深蹲掉力」
返回一堆「引体专项」标题块：**分数正常、排序单调、top5 都有内容，就是没答案**。

改法是每篇按序号旋转起点，并且在输出里打印结构分布（现在 动作明细 66 / 标题块 28 / 摘要 6）。
道理很朴素：**取样之后要看一眼「取到了什么」，而不是只看「取到几条」。**

## W5：向量没赢过 BM25（2026-11-15）

建了全量索引（3029 chunk × 1024 维，63.6 MB，76 秒），然后拿 15 道题、6 种方案去测它值不值得留。
**结果是我原来的假设错了：向量在三组切法下全部输给 BM25。**

| 方案 | Doc@1 | Doc@5 | Sec@1 | Sec@5 | MRR |
|---|---|---|---|---|---|
| **BM25 · 标题切** | **87%** | **100%** | **80%** | **100%** | **0.880** |
| 向量 · 标题切 | 73% | 93% | 73% | 93% | 0.843 |
| BM25 · H2 级 | 87% | 100% | 80% | 93% | 0.862 |
| 向量 · H2 级 | 60% | 87% | 60% | 87% | 0.711 |
| BM25 · 固定切 | 87% | 93% | 53% | 73% | 0.613 |
| 向量 · 固定切 | 47% | 80% | 27% | 73% | 0.480 |

三条可以直接读出来的：

1. **BM25 的 Doc@1 恒定 87%，完全不随切法变化；向量在 47%–73% 之间大幅波动。**
   BM25 对切法鲁棒，向量对切法敏感 —— 这比「谁赢」更有信息量。
2. **标题上下文对两边都关键，但对向量是生死线。** 固定切（无标题）时向量 Doc@1 只有 47%。
3. **向量唯一明显赢的一题是术语不一致**：题面「心率变异性」、语料 0 篇用这个词（223 篇用「HRV」），
   向量排第 1、BM25 排第 10。这是它真正的位置——不是普遍更强，而是**处理词表不重合**。

### 但「BM25 100%」这个数字要打折看

写题的时候我是看着语料写的，题面里的词和语料里的词是同一批。查了一遍：8 道「语义题」里
**只有 1 道是真正的跨术语题**（S3），其余 7 道都是同词匹配。这属于**出题者偏差**，
真实用户不会先读语料再提问（他会说「那个蹬腿的机器」）。

试过补一组纯口语题，做不下去——语料高度同质，任何不含日期、不含动作名的描述都能对上十几篇文档，
**ground truth 无法唯一**。这个失败本身也是结论：这份语料上语义检索的价值上限本来就低。

所以**暂时不换 BM25，也不删向量**，先做两件事再决定：把论述性语料（计划文档、知识笔记）进库，
以及补 10 道真·跨术语题。如果那时 BM25 还是赢，就痛快换掉。

细节、逐题排名、归因、五条「不能下的结论」：https://heoii.github.io/fitness-agent/retrieval.html

## W6：把检索接成一个人能问的入口（2026-11-15）

### 三个实测发现，每个都推翻了一个想当然

**① 上一轮报的「首 token 2844 ms」是测量错误。**

| 环节 | 实测 |
|---|---|
| 冷启动（遍历 3039 块 + 建 BM25 倒排） | 221 ms（190 + 31） |
| 加载向量库（64 MB JSON） | 305 ms |
| BM25 单次查询 | **0.7 ms**（P95 1.0） |
| 向量单次（嵌入 21 ms + 全扫 5 ms） | 26 ms |
| LLM 模型冷加载 + 首字（新进程首次） | 1523 ms |
| **LLM 首 token（热态，5 段上下文）** | **69–83 ms** |
| **生成速度（热态）** | **24 tok/s**（100 字 ≈ 4 s） |

上一轮我拿「带上下文首 token 2844 ms、13.4 tok/s」写下「瓶颈 100% 在生成」，
并据此把重心全押到「生成怎么更快」。**那个数错了**：2844 ms 里大部分是**模型加载**，
测的时候是新进程第一次提问，而紧接着的短问答只要 427 ms。差异不是上下文长度，是冷加载。
冷热分开后首 token 是 70 ms，原计划「首 token < 1.5 s」那条线**其实一直达得到**。

预热还有个更阴的坑：拿被测 case 自己的 prompt 去 warmup，会命中 Ollama 的
prompt 前缀缓存，测出 46 ms 这种假数。预热必须用无关短句。

**真正慢的是另外两件事，都不是「模型不行」**：

**② 本地 7B 不够用的是「算数」，不是「说话」。**

| 能力 | 结论 | 证据 |
|---|---|---|
| 不编造 | ✅ 通过 | 问「2019 年体脂率」（语料从 2025 起）→ 答「资料里没有找到」，没编数字 |
| 语言表述 | ✅ 通顺 | 能组织出带 `[1]` 引用的完整段落 |
| 算数 / 判趋势 | ❌ 不能给 | 把 1RM 82 kg 当成「最近一次深蹲重量」，与 60 kg 比，得出「在涨」 |

所以「要不要换云模型」这个问题暂时不成立：首字 70 ms 已比目标快 20 倍，
短板在用法不在模型。算数和判断必须由代码算好后作为字段喂进去。

**③ 拖后腿的是检索，而且根因很反直觉。**

问「深蹲最近在涨还是跌」，`top5` 里没有 11-07 和 11-14（排 #49 / #65），
模型只好拿 1RM 去比，推出「在涨」。查排名后发现 `top1` 是「HRV 口径切换」这种无关段落，
原因是：**「最近」这个词在整个语料里只出现在 11 块里**，DF 低意味着 IDF 极高
（比「深蹲」还高），于是「谁提过最近」压倒了「谁真的在讲深蹲」。

BM25 的 IDF 假设「稀有词 = 有信息量」，对实体词成立，对**时间副词和疑问词完全不成立**。
剥掉它们 + 加时间重排后：11-07 #49 → **#3**，11-14 #65 → **#4**。

另一个 query 上还有第二层原因：`--q "史密斯深蹲 容量"` 时 11-07 排 #17、11-14 排 #24，
因为「容量」出现在 1457 块里（48%，每个动作标题都带「— 容量 N」），区分度接近 0，
所有深蹲记录退化成分数几乎相同的 16.44 平票。但这类问题的真正解法不是调权重，
而是**根本不该走检索** —— 见下面「还没做」里的工具层。

顺带发现 tokenizer 把「8×8 和 5×5 的区别」切成 `["8","8","5","5"]`，
而「8」出现在 66.4% 的块里、「5」在 74.1% —— 排序完全由噪声决定。
修掉后 `top1` 是「卧推 8×8 / 5×5 怎么看」，得分 12.95，第二名 2.83。

### 检索层的分工

| 文件 | 是什么 |
|---|---|
| `src/lib/bm25.ts` | **评测基线**。一个测量工具，刻意不加任何预处理；改它，W5 的历史数字就失去可比性 |
| `src/lib/retrieve.ts` | **产品检索器**。BM25 + 查询清洗 + 时间重排 + 引用编号 |
| `src/lib/answer.ts` | **prompt 唯一出处**（和 `extract.ts` 同原则）。route 与评测脚本都从这里取 |

时间重排用两段式而不是直接改 BM25 打分：先取 top50 候选，再按
`bm25 × (0.55 + 0.45 × 时间因子)` 重排，返回里同时带 `bm25` 和 `recency`
—— 任何一次「它凭什么排第一」都能拆开看，不用去猜一堆乘在一起的权重。

## W7：算数不交给模型（2026-11-15）

四条入口，按「答案存在哪儿」分，不是按「问题长什么样」分：

| 入口 | 什么时候走 | 答案在哪 | 模型干什么 |
|---|---|---|---|
| `retrieve` | 语义题（为什么/怎么/是什么） | 某几段文字里 | 读片段、组织语言、标 `[n]` |
| `trend` | 涨了还是跌了 | 不存在于任何一段，要跨记录比 | 只说人话，不碰数字 |
| `count` | 一共几次 | 不存在于任何一段，要数全集 | 只说人话，不碰数字 |
| `latest` | 上次/最近一次是什么时候 | 不存在于任何一段，要取全库最晚 | 只说人话，不碰日期 |

**为什么必须分开**：W5 报告里 N6「深蹲在涨还是跌」发过一版「在涨」，后来发现是热身组污染；
W6 验收里 C2「这个月练了几次腿」答了「1 次」，依据是检索到的片段里有一句「11 月 4 日腿日被取消」。
两次都是**引用真实、推理成立、结论错**——这类错最难自查，因为答案带着出处，看起来查过了。
共同点是把 top5 当成了全集：top5 是「最相关的 5 条」，不是「全部 5 条」。
**计数和聚合只允许在全集上做，而现在只有语料遍历能提供全集。**

### 两条口径不是讲究，是数据本来就这样

工具层每个数字都带 `caliber`，因为这两处的口径差一档就能把结论翻过来：

- **容量含不含热身**：同一批深蹲记录，含热身 **+4.9%（基本持平）**，剔除热身 **−12.8%（在跌）**。
  练练写的 `capacity` 把热身组算进去了，多插一组热身就能让数变大，但那不是能力涨。
- **重点还是兼带**：`muscle_focus` 只记这节课**主要**练的部位，`muscle_groups` 是重点+辅助的并集。
  11-07 腿A 的 focus 是「腹/核心、腿、臀」，11-14 腿A 的 focus 只有「肩、腿」——臀在后者里是辅助。
  只报 focus 会得出「你没练臀」这种假结论。

所以工具不挑口径，两个都返回，prompt 里明令「两个都要报，只报一个会误导」。

### 定位入口是扩题库扩出来的

加 A9「最近一次游泳是什么时候」时，检索答了「资料里没有找到」——可库里明明有三天游泳记录。
查排名：真正记录 11-15 游泳的那篇排 **#32**，排在前面的是「次日准备」这类**计划**文档，
它们每篇都写着「游泳」，写的是打算，不是做过。

先修清洗（`次游`/`泳是` 这种跨词 bigram 混进了检索），排名从 #32 到 **#4**，进了 top5。
但模型看着 11-15 那一条，还是答「没有找到」——因为**答案根本不是某一段文字**，
它是全库上的 `max(date)`，还要排除计划里没发生的事。这和计数是同一类问题，
只是聚合函数不同（`max` 而不是 `count`），于是加了 `latest` 入口。

顺带一个 prompt 坑：给它「最近一次 11-14 / 更早一次 11-07」两行对照，7B 报了 **11-07**。
小模型在并列日期上很容易选错，改成「更早一次（**不是答案**）」并明令「不要报成这个日期」，
连跑三次都是 11-14。**判据只判「有没有引用」是不够的，还得判它报的日期对不对。**

### 探针抓到的两个静默 bug

`w7:count` 的判据表写的是**人工 grep 语料核对过的数字**，第一次跑就红了，两条都是「不报错只是少算」：

1. **有氧课数不到**。游泳课没有「动作明细」章节，`parseTraining` 返回 null，第一版用它过滤，
   整个游泳课就从计数里消失了——问「这个月有氧几次」直接回「没有记录」。
   改成：有动作明细就走解析，没有就退回 frontmatter 的 `muscle_focus`。
2. **`2024 年`被解析成 2026 年 11 月**。年份正则要求「YYYY-MM 或 YYYY 年 M 月」，裸年份掉进默认分支。
   问 2024 年答的是本月 2 次——**区间错的时候答案看起来完全正常**，这比报错危险得多。

两个 bug 都不是崩溃，都是「安静地给一个像样的数」。没有真值表，它们会一直在。

`w7:trend` 里「双杠臂屈伸」是**被拒**的：它既有 10kg 负重记录、又有纯自重记录，

这种时候不给结论比给一个更诚实。

### 延迟必须按冷热分开说

同一个全量验收，三次跑出来的平均端到端是 **2.4 s / 4.5 s / 7.8 s**，中间没有改任何性能相关的东西。
差别是 Ollama 的 prompt 前缀缓存：prompt 没变就是热态，改一个字的编号规则就退回冷态。
**所以「平均 4.5 s」这个数只对「同样的 prompt 连续问」成立**，拿它当产品延迟会低估一倍。
真正的口径在 `w6:latency`：冷加载 1523 ms、热态首 token 70 ms、检索 0.7 ms。

### 语料范围改变能力边界

`retrieve.ts` 支持 `KB_DIRS`（多目录），`tools.ts` 跟着用同一套优先级——两层读不同环境变量
是最难查的那种不一致（检索能跑、问趋势报「缺少 KB_DIR」）。

实测：只索引 `01 每日记录` 时，问「自由泳高肘抱水怎么练」，含「高肘」的块排 **#11**；
扩到整个知识库后同一块 **#1（25.63 分）**。原因很简单：「高肘」只出现在技术笔记里，
每日记录里没有——**这不是检索器的问题，是语料里根本没有答案**。
所以两个变量分开：`KB_DIR` 卡住边界给评测复现，`KB_DIRS` 放开给产品用。

## W7·5：流式与取消（2026-11-15）

### 流式真正解决的不是「首字慢」

首 token 热态实测 **70 ms**，从来不是瓶颈。难等的是**整句生成**：热态 24 tok/s，
一条 150 字的回答要 6 s，这 6 s 里页面是完全空白的。所以流式的第一个动作不是吐字：

**检索 14 ms，`cites` 事件先发。** 用户立刻看到「我用了哪 5 段资料、文件 > 标题是什么」——
如果找错了，他一眼就知道，不用等 6 秒读完一个基于错误资料的答案。
出字是顺带的收益，先给来源才是这一层的主要价值。

### 取消必须传到 Ollama

「前端不渲染了」不等于「模型停了」。不把 abort 传到对 Ollama 的 fetch，
用户关掉页面后模型还会把 260 个 token 跑完——从界面上**完全看不出来**，只能量时间。

判据：收到第 3 个 token 时 abort，要求 400 ms 内拿到 `aborted` 事件。
实测 **5 ms** 结束，说明 signal 一路传到了 fetch，Ollama 那边也断了。

顺带一个实现细节：`aborted` 和 `error` 是两个事件。用户主动取消不是错误，
页面上不该闪红色——把「他不想看了」显示成「系统出错了」是最让人恼火的一种反馈。

### 判据（`npm run w7:stream`）

| 判据 | 结果 |
|---|---|
| A `cites` 是第一个事件且字段完整 | 3/3 |
| B token 拼接 == `done.answer`（丢块就会对不上） | 2/2 |
| C 取消后 400 ms 内 `aborted` 收尾 | 1/1（实测 5 ms） |
| D `done` 里没有越界引用 | 2/2 |

### 判据自己的坑，又踩了一次

第一版把「中途取消」的用例算进了 B 和 D 的分母，于是 2/3 判失败——可那个用例
**根本没有 `done` 事件**，用「没发生」去判「不成立」。这和 `--only=C` 那次
显示「✓ A–D 全过」是同一个病：**分母里混进了不该判的样本**。
修法都是把分母改成「实际发生了这件事的样本」。

流式这件事在接口层还有一条：`Content-Type: text/event-stream` 必须配
`X-Accel-Buffering: no`，否则反向代理会攒满一块才吐，流式白做。

## W8：一个问题里有几个对象（2026-11-15）

### 先找到「静默答一半」这种错

多实体这件事不是猜出来的需求。加完定位入口后随手问了一句
「我上次腿课和上次胸课分别是什么时候」，答案是：

> [1] 最近一次腿课是 2026-11-14，距今 1 天。

**胸一个字都没有。** 没有报错，没有「我只答了一个」，界面上看起来是个完整的回答。

这比答错更难发现：答错你会去核对，答一半你不会。趋势入口更隐蔽——
问「深蹲和卧推哪个涨得多」，它只算了卧推（`matchExercise` 按频次返回一个），
深蹲完全没进上下文。那次是 7B 自己说了「深蹲的数据未提供」才露的馅，
**换个问题它就编下去了**。

根因是同一个：工具层是单实体的，问题里有几个对象它只处理一个。

### 先按连接词切，再逐段认实体

`entitiesIn()` 不做全串扫描。理由是全串扫描要处理「史密斯深蹲」里含「深蹲」、
「腿举」里含「腿」这类重叠；切成段之后每段只有一个实体，重叠问题自然消失，
认不出实体的段直接丢。

所以「热量和脂肪怎么分配」会被「和」切开，但两段都认不出实体，返回空——
**宁可不认，也不要把非实体当实体去调工具**。这条判据写进了 `w7:entity`。

### 不让模型决定「要不要再查一次」

控制循环通常的做法是让模型输出一个工具调用，自己决定查什么。这里没这么做，理由是实测：

- 本地 7B 的算数能力已经在 W7 被证明不可靠（N6 那次它把热身组算进容量，得出「在涨」）
- 一个连加法都会错的模型，让它自己决定「该查哪张表」，错了你连复现都难
- 规则驱动的多轮是**确定性**的：同一个问题永远走同一条路径，出错能定位到行

所以这一层是**预取式多实体展开**：先由规则判出「问题里有 3 个对象」，
分别调 3 次工具，把结果合并进一个 prompt。模型仍然只负责组织语言。
「模型自主决定再查一次」留到 M3 控制循环——那需要模型先把工具调用做对，现在还没有。

### 歧义：给默认答案，同时把其他候选的日期也报出来

问「上次硬拉是什么时候」，工具答 **2026-07-31，距今 107 天**。
数据是对的（那是「杠铃硬拉」的最近一次），但它误导：

| 动作 | 最近一次 | 距今 |
|---|---|---|
| 杠铃硬拉 | 2026-07-31 | 107 天 |
| 哑铃硬拉 | 2026-08-12 | 95 天 |
| 史密斯硬拉 | 2026-06-21 | 147 天 |
| **罗马尼亚硬拉** | **2026-10-30** | **16 天** |

语料里有五种硬拉，`matchExercise` 按频次选了杠铃。用户问的很可能就是罗马尼亚那种。

处理方式是**给默认答案 + 列出其他候选的日期**，不是拒绝回答——
拒绝会把「深蹲最近涨没涨」这种正常问题也挡掉（「深蹲」同样是 tail 层匹配）。

**这些日期由代码追加，不进 prompt。** 因为：

1. 实测 7B 在并列日期上会选错——A8 那次就给了它「最近一次 11-14 / 更早一次 11-07」，它报了 11-07
2. 候选日期没有引用编号（引用是给主答案准备的），让模型复述等于制造「有数字没出处」

所以 `Plan.trailer` 是代码写的一段，在生成之后拼上去。**模型碰不到它。**

### 多动作趋势：嘱咐没用，模板才有用

两个动作各两个口径 = 4 个百分比，其中 2 个方向相反。第一版 prompt 写的是
「每个对象的口径全都要报，不许只挑一个好看的结论」，模型的回答是：

> 史密斯深蹲 4.9% 基本持平；杠铃卧推 3.4% 基本持平。

**只报了「基本持平」那两个——正好是好看的那个。** 劝告式 prompt 在多对象上下文里形同虚设。

换成逐行填空模板：

```
- 史密斯深蹲｜含热身：<涨跌幅>% <结论>｜剔除热身：<涨跌幅>% <结论>
- 杠铃卧推｜含热身：<涨跌幅>% <结论>｜剔除热身：<涨跌幅>% <结论>
```

改完连跑两次，输出字节一致，四个数字全对。**约束结构比约束意图有效。**

模板之后还留了条口子「最多再加一句总结」，结果它写「杠铃卧推在两个口径下均有所下降」——
表格里剔除热身明明是 3.4% 基本持平。**总结和表格打架比没有总结更糟**，改成禁止自由总结。

### 元指令泄漏

`TrendResult.summary` 里原本带着一句写给模型的指令：
「**两个都要报，不能只挑一个**，并说明「涨的那部分可能来自热身组」」。
模型把它当结论抄进了答案，用户看到的是：

> …差异来自热身组占比。两个都要报，不能只挑一个，并说明「涨的那部分可能来自热身组」。

数据字段里只放事实，指令放 prompt 的要求区。混在一起就会被原样复述。

### 判据（`npm run w7:multi`，不调模型）

测的是路由和工具，不是模型稳不稳定——混在一起测，模型抖一下会让人以为路由坏了。

| 判据 | 结果 |
|---|---|
| 引用条数 == 各实体之和 | 7/7 |
| 多实体不共用同一篇文档（共用 = 后一个没查） | 3/3 |
| 单实体路径 k 与改造前一致 | 4/4 |
| 歧义提示出现（硬拉→罗马尼亚/史密斯） | 1/1 |

端到端仍然由 `w6:ask` 把关：改完复跑全套，A/B/C/D/E/F 全过（当时 19 题）。
单实体的 prompt 是逐字保留下来的（`buildCountPrompt` / `buildTrendPrompt` 里
`length === 1` 的分支），**加功能不该顺手改动已经验过的东西**。

## W9：有些问题的前提就是错的（2026-11-15）

### 一个「跳过了一半」的答案

问「减载期、恢复期、增长期的门槛分别是什么」，模型答：

> 减载期 ACWR < 0.8；增长期 ACWR 0.8–1.3；过载/高危区 ACWR > 1.3。

三个区间都对，但它**没回答「恢复期」**——而用户问的就是那一个。

去查语料，2026-10-31 那篇里有一整节叫《最容易混的一对：减载 ≠ 恢复》：

- **减载**：主动的、计划内的、5–7 天。减容量不减重量。
- **恢复**：被动的、被外力打断（生病/受伤/生活事件）、2–4 周。先判能不能练。

所以问题本身就是混的：减载/增长是 **ACWR 的三个区间**，而「恢复」是**另一套划分**，
两者不在同一层。不存在「恢复期的 ACWR 门槛」这个东西。

模型做了件「看起来安全」的事——只答它确定的，把答不上的跳过。结果是最糟的一种：
**它顺着错的框架答，还漏了一个，而这两件事都没有留下任何痕迹。**

### 补一条规则，并盯着它别过度触发

`buildAskPrompt` 加了第 4 条：

> **如果问题的前提本身就被资料纠正了，先说纠正，再回答。**（…）顺着错的框架答，
> 用户会以为自己的理解没问题——那比答不出更糟。**资料里没有这种纠正时不要硬找。**

加完 A2 变成：

> 这两个不是一回事。减载期/增长区的门槛如下：…… 恢复期不是上述划分的一部分，
> 而是指被动的、被迫的、持续 2–4 周的中断期，与减载期和增长区的概念不同。

关键是**过度触发**——prompt 第 4 条在 W6 就翻过一次车（把「这需要结构化统计」挂在每个回答后面）。
所以加完立刻查了三条不该触发的：A10「蛋白粉最多几勺」直接答「一天一勺」，
B3/B4 直接答「资料里没有找到」。都没有额外的「不过你要注意」。

判据 `F` 只认「有没有指出这不是一回事」，不判措辞漂不漂亮——那太脆。
但 `mustMention` 是硬的：光说「不是一回事」却不讲恢复是什么，等于没回答。

### 更值得记的是：延迟那个数字不可信

改完 prompt 跑全量，平均端到端从 **2.7 s 涨到 5.4 s**。第一反应是「prompt 变长了」。

于是做了三件事：

1. 对比答案字数——**几乎没变**（19 题里 12 题 +0，最大变化 +79 字）
2. 分路径看——`count`（2.3→2.6 s）和 `latest`（1.5→1.6 s）**完全没变**，只有 `retrieve` 变慢
3. 同一份代码**连续跑三次**：5.4 → 4.3 → 3.9 s

结论：**这个均值当天在 2.7–5.4 s 之间飘，它不是代码变慢，是测量状态在变**
（模型冷热、机器负载）。单题热态一直是 1.1–1.6 s，那个数才稳定。

所以文档里不该只写「4.5 s」这种单点值。现在写的是
「单题热态 1.1–1.6 s；全量 19 题均值 3.8 s，当天在 2.7–5.4 s 之间飘过」。

这和 W6 那次「首 token 2844 ms」是同一个病：**报了一个没控制变量的数**。
区别是这次在报之前就发现了。

|---|---|
| A 引用合法 | 19/19 |
| B 引用可定位 | 19/19 |

## W10：没有对象的问题（2026-11-15）

22 题全过之后，反过来做了一件事：**故意找边界**。19 题全过只说明题库不够难，
不说明系统有边界意识。随手打了三个问题，塌了两个——而且塌法完全不同。

### 三种塌法，只有一种是该塌的

| 问题 | 表现 | 判定 |
|---|---|---|
| 哪些动作我从来没练过 | 拒答 | **正确**。语料里只有练过的 136 个动作，没有动作全集，答不了就是答不了 |
| 我平均每周练几次 | 答「每周 4-5 次」 | **错**。依据是「10 月平均间隔 1.5 天」——引用真实、算术也对，但答的是十月 |
| 和上个月比这个月练得更多吗 | 拒答 | **错**。两个区间的课数相减，工具层完全能算 |

第二个最值得说：它没有编数字，它是**从一段文字里抄了个数，再自己做了除法**。
1.5 天 → 每周 4.67 次。每一步都成立，唯一的问题是「10 月的数据」不能回答「平均每周」。
这和 C1 深蹲那次是同一个病，只是那次是加法、这次是除法。

根因是工具层要求「必须有部位或动作」：`entitiesIn` 返回空就 `return null`，
于是一切「问总量」的题都掉进检索。可「练了几次」「每周几次」「比上月多吗」
本来就没有对象——它们问的是**集合本身**。

### perWeek 的分母：最容易错、也最看不见

补 `countTraining({ period })`（三个参数都不传 = 数全部）之后，
`perWeek` 立刻遇到一个问题：11-15 问「本月平均每周几次」，分母是 30 还是 15？

用 30 会把**还没到的半个月**算成「没练」，频率直接砍半（10 次 → 每周 2.3 而不是 4.7）。
所以分母取 `min(区间末, 今天)`：

```ts
const endMs = Math.min(Date.parse(period.to), ref.getTime());
const days = Math.round((endMs - Date.parse(period.from)) / 86_400_000) + 1;
```

判据这一条专门写了一项：本月 `perWeek.days === 15`、上月 `=== 31`。
两个数字只要换一下，整个「练得多少」的结论就反了，而**答案读起来完全正常**。

### 对比题整条答案由代码算，不过模型

「这个月比上个月练得更多吗」的每个字都是模板化的：两个月各几次、每周几次、差多少。
让 7B 复述只会引入新的错法，而这里是纯算术，代码不会算错。

所以 `route=compare` 是 `prompt: null` + `fixedAnswer`，**1 ms 出答案**。
实测：

> 2026 年 11 月（2026-11-01 ~ 2026-11-30，已过 15 天）：10 次，每周 4.7 次
> 2026 年 10 月（2026-10-01 ~ 2026-10-31，已过 31 天）：26 次，每周 5.9 次
> 按每周频率比：-21%（4.7 vs 5.9 次/周），这个月练得更少。
> 注：只比次数，不比训练量——容量跨动作不可相加。

**同时报总次数和每周频率**，理由和「含热身 / 剔除热身」一样：
本月才过一半，总次数少 16 次，但那不代表练得少。一个数两种读法，都得给。

### 判据 B 的分母变了，但不是放松

`compare` 没有引用——它的答案来自「遍历全部训练记录」，不是某一篇。
硬配两条引用等于暗示答案出自那两篇，比不给更误导。

所以 B（引用可定位）的分母排除聚合类：19/19 而不是 22/22。
**这和 `--only=C` 那次的空洞通过不是一回事**：那次是判据压根没跑却报「全过」，
这里是明确排除不适用的一类，分母变小且看得见。

### 又一次：均值是个会骗人的数

加完三题（两道 `compare` 1 ms、一道 `count` 有模型），全量均值从 **3.8 s 掉到 2.5 s**。

其他 19 道题一行代码没动，一点没变快。**均值被三道 0 ms 的题稀释了。**

这和 W9 末尾那个「2.7 → 5.4 → 3.9」是同一件事的两面：
**报一个平均数，等于让别人无法判断你测的是什么。**
现在文档里写的是「单题热态 1.1–1.6 s」——那个数才稳定。

### 判据（`npm run w7:agg`，固定参考日 2026-11-15）

`w6:ask` 的 G1–G3 用的是「今天」算出来的真值（11 月 10 篇、10 月 26 篇），
**跨月会全部变红**——红了是提醒重算真值，但一个会过期的判据不能当回归基线。
所以另写了一份用固定日期的：

| 判据 | 结果 |
|---|---|
| 2026-11 总课数 10 / 2026-10 总课数 26（人工 `ls` 数过） | 2/2 |
| `perWeek.days`：本月 15（已过）、上月 31（整月） | 2/2 |
| 每周频率 4.67（用精确天数，不是四舍五入后的周数） | 1/1 |
| 月/周对比的四个边界（月初、月末、周一、周日） | 7/7 |
| 「上个月练了几次」不被当成对比 | 1/1 |
| 空区间不冒充 0 次 | 1/1 |

## W11：哪些动作我很久没练（2026-11-15）

### 先说清什么是算不出来的

「哪些动作我**从来**没练过」——这个问题算不了，而且不是因为难，是因为**数据里没有**。

语料里只有你练过的动作（135 个）。`action_muscles.json` 是从训练记录反推的肌群映射，
数据源 free-exercise-db 有 876 条，但仓库里只保存了用到的这些。
所以「没练过」这个名字集合不存在。

关键是**别把它和「很久没练」混起来**：前者要全集，后者只需在已有集合上取日期。
混起来的后果很坏——用户会以为那些动作自己真的没碰过，而它们只是没被记录。

所以两条路径分开，而且「从来没」那条直接把边界说出来：

> 列不出来：语料里只有你练过的动作（共 135 个），没有完整动作库，
> 所以「从来没练过」这个名字集合不存在。
> 能算的是反过来的那个：**哪些动作很久没练**——问我就行。

**空答案 + 给出相邻的能力**，比「资料里没有找到相关内容」有用得多：
后者暗示「系统什么都没查到」，而实际上系统很清楚自己缺什么。

### 「很久没练」是集合差 + 日期

对每个动作取 `max(date)`，按距今天数排序。任何一段文字里都没有这个结果，
模型也算不了——它得先记住一百多个动作各自的最近日期。

实测（2026-11-15）：

> [1] 悍马上斜推胸：最近一次 2025-08-05，距今 467 天，共练过 1 次
> …
> 语料里共 135 个动作，超过 30 天没练的有 **92** 个。

这条也**不过模型**（`prompt: null` + `fixedAnswer`）：答案是结构化列表，
让 7B 复述 5 个日期它一定会抄错一个。

### 意图过宽：问硬拉，答了排行榜

第一版只要命中 `/多久没练/` 就走这条，于是「硬拉多久没练了」得到的是**全局最久没练 top5**：

> [1] 悍马上斜推胸：最近一次 2025-08-05，距今 467 天

用户问的是硬拉。这个答案不但答错，还**长得像个正确答案**——
列表格式规整、有日期有天数和引用，一眼看不出答的是另一个问题。

修法是加一句前置判断：认出具体动作/部位就 `return null`，交给 `latest`。
这和 W8 的「多实体」是同一类错误的两个方向：
那边是**该分的没分**（只答一个对象），这边是**该收的没收**（把范围放大到全局）。

### 附带一个更值得记的：人工核对也会错

写探针时想验「动作总数」，用 shell 数了一遍：

```bash
grep -h "^### " 20*-*-训练*.md | sed 's/^### //; s/（kg）.*//' | sort -u | wc -l
# → 141
```

工具说 135。差 6 个，看着像工具漏了——和之前「游泳课没动作明细，整篇从计数里消失」
是同一类静默 bug。于是去 diff，结果这 6 个是：

```
一、执行 vs 计划
三、与历史比，练成了什么样
五、今天
```

**是章节标题**。它们以 `### ` 开头，被我的 grep 当成了动作名。

所以「人工核对过的真值」这句话得打个折：人工核对也会错，而且错得理直气壮——
我当时已经准备去改 `parseTraining` 了。真正的判据是**两套独立方法得出同一个数**，
而不是「我亲手数的所以一定对」。

### 均值又掉了一次

## 三个设计取舍

1. **单一出处**：prompt、输入清洗、校验只在 `src/lib/extract.ts` 写一份，接口和测试都 import 它。
   两份实现必然漂移，改了接口那份忘了测试那份，测试会一直绿着而线上已错。
2. **按最坏情况给 token 预算**（2000 而非 900）：代价是延迟上升，换来截断概率归零。
   短记录不受影响——预算是上限不是固定开销。
3. **失败不抛异常**：返回 `{ok:false, raw, issues}`。接口永远不 500，调用方永远拿得到能处理的东西。

  `countTraining` 已经能按 `muscle_focus` 数到它（2026-11 有氧 3 次），但「游得比以前快不快」还没入口。
- **只有 20 篇**：样本量够说明稳定性，不够说明分布外泛化。213 篇力量记录里还有 193 篇没进过评测。
- **检索对 query 措辞敏感**：`w6:debug` 可以复现——同一个意图换个说法，top5 会变。
  现在靠「清洗掉时间副词/疑问词 + 时间重排」压住了已知的几类，但没有查询改写的通用机制。
- **命中子块会丢父节上下文**：问「练胸为什么脖子酸」时命中的是「明天怎么办」那个子节，
