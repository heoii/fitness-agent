# fitness-agent

从个人训练记录里抽取结构化数据的 Agent 项目。目标不是"做个健身 App"，是把 LLM 应用的工程链路跑通：
结构化输出 → 检索 → 流式 → 控制循环 → 评测。

**实测报告（可直接看）：https://heoii.github.io/fitness-agent/**

## 它是怎么工作的

两条链路，共用一个模型和一份 prompt 出处。

```
① 抽取（W2）
训练记录 md
  → 输入清洗（只留「动作明细 / 训练摘要」段，切掉复盘、下次计划）
  → prompt（字段口径固定，禁止新增/改名）
  → qwen2.5:7b-instruct（temperature=0, format=json）
  → 闸一 JSON.parse      能不能读
  → 闸二 Zod             字段对不对
  → 闸三 字段比对         内容对不对（测试脚本独有）
  → ok / 兜底（永不 500）

② 问答（W6）
问题（用户原话）
  → 查询清洗（剥掉「最近 / 还是 / 为什么」这类词）   ← 为什么必须剥：「最近」在
                                                     这个语料里 DF 极低 → IDF 比「深蹲」还高
  → BM25 取 top50
  → 时间重排  score × (0.55 + 0.45 × 时间因子)      ← 用户说「最近」时半衰期 45 天
  → top5 组装成 [1]..[5]
  → qwen2.5:7b-instruct（明令禁止自己算数）
  → 引用校验：答案里的 [n] 必须都 ≤ 5，越界就是编引用
  → 答不出 → 「资料里没有找到」，不编
```

## 失败过什么（三轮）

20 篇力量记录现在 20/20。这个数字之前的每一步都是被真实失败推着走的，不是一次写对的：

| 轮次 | 结果 | 真实原因 | 改法 |
|---|---|---|---|
| 11-14 第一轮 | 17/20 | 输出预算 900 tok 截断 ×2；prompt 没给 session 取法 | 预算提到 2000；prompt 补 session 规则 |
| 11-14 第二轮 | 19/20 | `2026-10-22` 同篇里有「教练复盘」+「下次处方表」，模型把处方当成训练记录 | 输入侧只喂记录段（`trimToRecord`） |
| 11-15 第三轮 | 20/20 | 同一篇里同名动作出现两次，模型合并后补了一个 `reps: null` 空组 | prompt 加「同名动作各算一个，不许补空组」 |

第三轮还顺手修了一处校准错误：模型对可省字段给 `null` 而非省略，schema 只认省略，于是整条被判不合规。
`null` 与缺失同义 → 归一化成 `undefined`，但类型错（字符串、负数）照旧拦。

## 切片为什么不按字数切（W3）

语料的语义边界就是标题：`## 动作明细` 下是一组动作、`## 摘要` 是一句话结论。按固定字数切
（512 token 滑窗那套）会把「1RM 的定义」切成上一块结尾 + 下一块开头，检索命中一个也读不懂。

所以切两层：主边界 `##`；若该段里还有 `###` 就继续细到叶子，但 `headingPath` 保留完整父级
（`动作明细 > 史密斯深蹲（kg）— 容量 2060`）。训练记录的 `## 动作明细` 有 8 个动作、700 多字，
整段做成一个 chunk 语义太杂——问「深蹲掉力」会命中整段，前 5 条近邻全是同一篇的其他动作。

过短块（`## 摘要` 那种一句话）**不在切片阶段合并**：合并属于检索调优，W5 看 recall 再定。
切片只负责不丢内容、可回溯。

## 两个「看起来没坏」的错（W3/W4）

这两个都不是崩溃，都是**结果看着正常、结论全错**，所以单独记一节：

**① CRLF 让 235 篇的标题全部失效。** 语料里 235/989 篇是 Windows 写的 CRLF。`split("\n")` 之后
行尾还挂着 `\r`，而标题正则的 `(.*)$` 里 `.` 不匹配 `\r`、`$` 又只认整串结尾 —— 于是**每一个标题
都匹配不上**，整篇塌成一个无标题大块，`headingPath` 变空，检索时引用不到任何小节。

它能活到 W4 才被发现，是因为 W3 那条判据**自指**：「headingPath 每级都出现在本文档标题行里」——
用它自己的同一个正则去核对，两边同时失败就互相印证成「通过」。现在的改法两层：`loadDoc` 统一
换行符（单一出处，下游不用各自防），判据加一条独立的「有标题的文档不许切出空路径块」。
修完 chunk 数 2624 → 3045、超长硬切 148 → 40。

**② 取样偏差让样本里根本没有答案。** W4 第一版按文档轮转取 100 条，结果 98/100 都是文档标题块——
训练记录的第一块永远是标题块，`## 动作明细` 那种带动作数据的块一条进不来。表现是问「深蹲掉力」
返回一堆「引体专项」标题块：**分数正常、排序单调、top5 都有内容，就是没答案**。

改法是每篇按序号旋转起点，并且在输出里打印结构分布（现在 动作明细 66 / 标题块 28 / 摘要 6）。
道理很朴素：**取样之后要看一眼「取到了什么」，而不是只看「取到几条」。**

## W5：向量没赢过 BM25（2026-11-15）

建了全量索引（3029 chunk × 1024 维，63.6 MB，76 秒），然后拿 15 道题、6 种方案去测它值不值得留。
**结果是我原来的假设错了：向量在三组切法下全部输给 BM25。**

| 方案 | Doc@1 | Doc@5 | Sec@1 | Sec@5 | MRR |
|---|---|---|---|---|---|
| **BM25 · 标题切** | **87%** | **100%** | **80%** | **100%** | **0.880** |
| 向量 · 标题切 | 73% | 93% | 73% | 93% | 0.843 |
| BM25 · H2 级 | 87% | 100% | 80% | 93% | 0.862 |
| 向量 · H2 级 | 60% | 87% | 60% | 87% | 0.711 |
| BM25 · 固定切 | 87% | 93% | 53% | 73% | 0.613 |
| 向量 · 固定切 | 47% | 80% | 27% | 73% | 0.480 |

三条可以直接读出来的：

1. **BM25 的 Doc@1 恒定 87%，完全不随切法变化；向量在 47%–73% 之间大幅波动。**
   BM25 对切法鲁棒，向量对切法敏感 —— 这比「谁赢」更有信息量。
2. **标题上下文对两边都关键，但对向量是生死线。** 固定切（无标题）时向量 Doc@1 只有 47%。
3. **向量唯一明显赢的一题是术语不一致**：题面「心率变异性」、语料 0 篇用这个词（223 篇用「HRV」），
   向量排第 1、BM25 排第 10。这是它真正的位置——不是普遍更强，而是**处理词表不重合**。

### 但「BM25 100%」这个数字要打折看

写题的时候我是看着语料写的，题面里的词和语料里的词是同一批。查了一遍：8 道「语义题」里
**只有 1 道是真正的跨术语题**（S3），其余 7 道都是同词匹配。这属于**出题者偏差**，
真实用户不会先读语料再提问（他会说「那个蹬腿的机器」）。

试过补一组纯口语题，做不下去——语料高度同质，任何不含日期、不含动作名的描述都能对上十几篇文档，
**ground truth 无法唯一**。这个失败本身也是结论：这份语料上语义检索的价值上限本来就低。

所以**暂时不换 BM25，也不删向量**，先做两件事再决定：把论述性语料（计划文档、知识笔记）进库，
以及补 10 道真·跨术语题。如果那时 BM25 还是赢，就痛快换掉。

细节、逐题排名、归因、五条「不能下的结论」：https://heoii.github.io/fitness-agent/retrieval.html

## W6：把检索接成一个人能问的入口（2026-11-15）

### 三个实测发现，每个都推翻了一个想当然

**① 上一轮报的「首 token 2844 ms」是测量错误。**

| 环节 | 实测 |
|---|---|
| 冷启动（遍历 3039 块 + 建 BM25 倒排） | 221 ms（190 + 31） |
| 加载向量库（64 MB JSON） | 305 ms |
| BM25 单次查询 | **0.7 ms**（P95 1.0） |
| 向量单次（嵌入 21 ms + 全扫 5 ms） | 26 ms |
| LLM 模型冷加载 + 首字（新进程首次） | 1523 ms |
| **LLM 首 token（热态，5 段上下文）** | **69–83 ms** |
| **生成速度（热态）** | **24 tok/s**（100 字 ≈ 4 s） |

上一轮我拿「带上下文首 token 2844 ms、13.4 tok/s」写下「瓶颈 100% 在生成」，
并据此把重心全押到「生成怎么更快」。**那个数错了**：2844 ms 里大部分是**模型加载**，
测的时候是新进程第一次提问，而紧接着的短问答只要 427 ms。差异不是上下文长度，是冷加载。
冷热分开后首 token 是 70 ms，原计划「首 token < 1.5 s」那条线**其实一直达得到**。

预热还有个更阴的坑：拿被测 case 自己的 prompt 去 warmup，会命中 Ollama 的
prompt 前缀缓存，测出 46 ms 这种假数。预热必须用无关短句。

**真正慢的是另外两件事，都不是「模型不行」**：

**② 本地 7B 不够用的是「算数」，不是「说话」。**

| 能力 | 结论 | 证据 |
|---|---|---|
| 不编造 | ✅ 通过 | 问「2019 年体脂率」（语料从 2025 起）→ 答「资料里没有找到」，没编数字 |
| 语言表述 | ✅ 通顺 | 能组织出带 `[1]` 引用的完整段落 |
| 算数 / 判趋势 | ❌ 不能给 | 把 1RM 82 kg 当成「最近一次深蹲重量」，与 60 kg 比，得出「在涨」 |

所以「要不要换云模型」这个问题暂时不成立：首字 70 ms 已比目标快 20 倍，
短板在用法不在模型。算数和判断必须由代码算好后作为字段喂进去。

**③ 拖后腿的是检索，而且根因很反直觉。**

问「深蹲最近在涨还是跌」，`top5` 里没有 11-07 和 11-14（排 #49 / #65），
模型只好拿 1RM 去比，推出「在涨」。查排名后发现 `top1` 是「HRV 口径切换」这种无关段落，
原因是：**「最近」这个词在整个语料里只出现在 11 块里**，DF 低意味着 IDF 极高
（比「深蹲」还高），于是「谁提过最近」压倒了「谁真的在讲深蹲」。

BM25 的 IDF 假设「稀有词 = 有信息量」，对实体词成立，对**时间副词和疑问词完全不成立**。
剥掉它们 + 加时间重排后：11-07 #49 → **#3**，11-14 #65 → **#4**。

另一个 query 上还有第二层原因：`--q "史密斯深蹲 容量"` 时 11-07 排 #17、11-14 排 #24，
因为「容量」出现在 1457 块里（48%，每个动作标题都带「— 容量 N」），区分度接近 0，
所有深蹲记录退化成分数几乎相同的 16.44 平票。但这类问题的真正解法不是调权重，
而是**根本不该走检索** —— 见下面「还没做」里的工具层。

顺带发现 tokenizer 把「8×8 和 5×5 的区别」切成 `["8","8","5","5"]`，
而「8」出现在 66.4% 的块里、「5」在 74.1% —— 排序完全由噪声决定。
修掉后 `top1` 是「卧推 8×8 / 5×5 怎么看」，得分 12.95，第二名 2.83。

### 检索层的分工

| 文件 | 是什么 |
|---|---|
| `src/lib/bm25.ts` | **评测基线**。一个测量工具，刻意不加任何预处理；改它，W5 的历史数字就失去可比性 |
| `src/lib/retrieve.ts` | **产品检索器**。BM25 + 查询清洗 + 时间重排 + 引用编号 |
| `src/lib/answer.ts` | **prompt 唯一出处**（和 `extract.ts` 同原则）。route 与评测脚本都从这里取 |

时间重排用两段式而不是直接改 BM25 打分：先取 top50 候选，再按
`bm25 × (0.55 + 0.45 × 时间因子)` 重排，返回里同时带 `bm25` 和 `recency`
—— 任何一次「它凭什么排第一」都能拆开看，不用去猜一堆乘在一起的权重。

### 验收（`npm run w6:ask`，11 题）

### 两条自我修正

  连「减载期门槛」「高肘抱水」这种纯语义题也被挂上，变成噪声。改成条件式后消失。
- **判据比实现更容易出错**：E 那条第一版只匹配「这需要结构化统计」，
  而 C1 明明答了「没有信息表明这些变化是持续的趋势，因此无法判断」——

## W7：算数不交给模型（2026-11-15）

四条入口，按「答案存在哪儿」分，不是按「问题长什么样」分：

| 入口 | 什么时候走 | 答案在哪 | 模型干什么 |
|---|---|---|---|
| `retrieve` | 语义题（为什么/怎么/是什么） | 某几段文字里 | 读片段、组织语言、标 `[n]` |
| `trend` | 涨了还是跌了 | 不存在于任何一段，要跨记录比 | 只说人话，不碰数字 |
| `count` | 一共几次 | 不存在于任何一段，要数全集 | 只说人话，不碰数字 |
| `latest` | 上次/最近一次是什么时候 | 不存在于任何一段，要取全库最晚 | 只说人话，不碰日期 |

**为什么必须分开**：W5 报告里 N6「深蹲在涨还是跌」发过一版「在涨」，后来发现是热身组污染；
W6 验收里 C2「这个月练了几次腿」答了「1 次」，依据是检索到的片段里有一句「11 月 4 日腿日被取消」。
两次都是**引用真实、推理成立、结论错**——这类错最难自查，因为答案带着出处，看起来查过了。
共同点是把 top5 当成了全集：top5 是「最相关的 5 条」，不是「全部 5 条」。
**计数和聚合只允许在全集上做，而现在只有语料遍历能提供全集。**

### 两条口径不是讲究，是数据本来就这样

工具层每个数字都带 `caliber`，因为这两处的口径差一档就能把结论翻过来：

- **容量含不含热身**：同一批深蹲记录，含热身 **+4.9%（基本持平）**，剔除热身 **−12.8%（在跌）**。
  练练写的 `capacity` 把热身组算进去了，多插一组热身就能让数变大，但那不是能力涨。
- **重点还是兼带**：`muscle_focus` 只记这节课**主要**练的部位，`muscle_groups` 是重点+辅助的并集。
  11-07 腿A 的 focus 是「腹/核心、腿、臀」，11-14 腿A 的 focus 只有「肩、腿」——臀在后者里是辅助。
  只报 focus 会得出「你没练臀」这种假结论。

所以工具不挑口径，两个都返回，prompt 里明令「两个都要报，只报一个会误导」。

### 定位入口是扩题库扩出来的

加 A9「最近一次游泳是什么时候」时，检索答了「资料里没有找到」——可库里明明有三天游泳记录。
查排名：真正记录 11-15 游泳的那篇排 **#32**，排在前面的是「次日准备」这类**计划**文档，
它们每篇都写着「游泳」，写的是打算，不是做过。

先修清洗（`次游`/`泳是` 这种跨词 bigram 混进了检索），排名从 #32 到 **#4**，进了 top5。
但模型看着 11-15 那一条，还是答「没有找到」——因为**答案根本不是某一段文字**，
它是全库上的 `max(date)`，还要排除计划里没发生的事。这和计数是同一类问题，
只是聚合函数不同（`max` 而不是 `count`），于是加了 `latest` 入口。

顺带一个 prompt 坑：给它「最近一次 11-14 / 更早一次 11-07」两行对照，7B 报了 **11-07**。
小模型在并列日期上很容易选错，改成「更早一次（**不是答案**）」并明令「不要报成这个日期」，
连跑三次都是 11-14。**判据只判「有没有引用」是不够的，还得判它报的日期对不对。**

### 探针抓到的两个静默 bug

`w7:count` 的判据表写的是**人工 grep 语料核对过的数字**，第一次跑就红了，两条都是「不报错只是少算」：

1. **有氧课数不到**。游泳课没有「动作明细」章节，`parseTraining` 返回 null，第一版用它过滤，
   整个游泳课就从计数里消失了——问「这个月有氧几次」直接回「没有记录」。
   改成：有动作明细就走解析，没有就退回 frontmatter 的 `muscle_focus`。
2. **`2024 年`被解析成 2026 年 11 月**。年份正则要求「YYYY-MM 或 YYYY 年 M 月」，裸年份掉进默认分支。
   问 2024 年答的是本月 2 次——**区间错的时候答案看起来完全正常**，这比报错危险得多。

两个 bug 都不是崩溃，都是「安静地给一个像样的数」。没有真值表，它们会一直在。

### 验收

| 探针 | 判据 |
|---|---|
| `w7:trend` | 双口径完整 3/3、差额能被热身占比解释 3/3、降级课排除 3 次、歧义给候选 1 个用例 |
| `w7:count` | 次数对真值 4/4、不串月 4/4、兼带≥重点 4/4、降级课识别 1/1、空区间不冒充 0 次 1/1 |
| `w7:latest` | 日期对真值 4/4、daysAgo 一致 4/4、previous 严格更早 4/4、没有的目标报错 1/1 |
| `w6:ask`（19 题） | A 19/19、B 19/19、C 10/10、D 4/4、E 5/5；分类 **语义 10/10 · 拒答 4/4 · 算数 5/5** |

`w7:trend` 里「双杠臂屈伸」是**被拒**的：它既有 10kg 负重记录、又有纯自重记录，
两种容量不同量纲，硬算会得出「在跌 92.4%」——数字来自单位换算，不是能力变化。
这种时候不给结论比给一个更诚实。

### 延迟必须按冷热分开说

同一个全量验收，三次跑出来的平均端到端是 **2.4 s / 4.5 s / 7.8 s**，中间没有改任何性能相关的东西。
差别是 Ollama 的 prompt 前缀缓存：prompt 没变就是热态，改一个字的编号规则就退回冷态。
**所以「平均 4.5 s」这个数只对「同样的 prompt 连续问」成立**，拿它当产品延迟会低估一倍。
真正的口径在 `w6:latency`：冷加载 1523 ms、热态首 token 70 ms、检索 0.7 ms。

### 语料范围改变能力边界

`retrieve.ts` 支持 `KB_DIRS`（多目录），`tools.ts` 跟着用同一套优先级——两层读不同环境变量
是最难查的那种不一致（检索能跑、问趋势报「缺少 KB_DIR」）。

实测：只索引 `01 每日记录` 时，问「自由泳高肘抱水怎么练」，含「高肘」的块排 **#11**；
扩到整个知识库后同一块 **#1（25.63 分）**。原因很简单：「高肘」只出现在技术笔记里，
每日记录里没有——**这不是检索器的问题，是语料里根本没有答案**。
所以两个变量分开：`KB_DIR` 卡住边界给评测复现，`KB_DIRS` 放开给产品用。

## W7·5：流式与取消（2026-11-15）

### 流式真正解决的不是「首字慢」

首 token 热态实测 **70 ms**，从来不是瓶颈。难等的是**整句生成**：热态 24 tok/s，
一条 150 字的回答要 6 s，这 6 s 里页面是完全空白的。所以流式的第一个动作不是吐字：

**检索 14 ms，`cites` 事件先发。** 用户立刻看到「我用了哪 5 段资料、文件 > 标题是什么」——
如果找错了，他一眼就知道，不用等 6 秒读完一个基于错误资料的答案。
出字是顺带的收益，先给来源才是这一层的主要价值。

### 取消必须传到 Ollama

「前端不渲染了」不等于「模型停了」。不把 abort 传到对 Ollama 的 fetch，
用户关掉页面后模型还会把 260 个 token 跑完——从界面上**完全看不出来**，只能量时间。

判据：收到第 3 个 token 时 abort，要求 400 ms 内拿到 `aborted` 事件。
实测 **5 ms** 结束，说明 signal 一路传到了 fetch，Ollama 那边也断了。

顺带一个实现细节：`aborted` 和 `error` 是两个事件。用户主动取消不是错误，
页面上不该闪红色——把「他不想看了」显示成「系统出错了」是最让人恼火的一种反馈。

### 判据（`npm run w7:stream`）

| 判据 | 结果 |
|---|---|
| A `cites` 是第一个事件且字段完整 | 3/3 |
| B token 拼接 == `done.answer`（丢块就会对不上） | 2/2 |
| C 取消后 400 ms 内 `aborted` 收尾 | 1/1（实测 5 ms） |
| D `done` 里没有越界引用 | 2/2 |

### 判据自己的坑，又踩了一次

第一版把「中途取消」的用例算进了 B 和 D 的分母，于是 2/3 判失败——可那个用例
**根本没有 `done` 事件**，用「没发生」去判「不成立」。这和 `--only=C` 那次
显示「✓ A–D 全过」是同一个病：**分母里混进了不该判的样本**。
修法都是把分母改成「实际发生了这件事的样本」。

流式这件事在接口层还有一条：`Content-Type: text/event-stream` 必须配
`X-Accel-Buffering: no`，否则反向代理会攒满一块才吐，流式白做。

## 三个设计取舍

1. **单一出处**：prompt、输入清洗、校验只在 `src/lib/extract.ts` 写一份，接口和测试都 import 它。
   两份实现必然漂移，改了接口那份忘了测试那份，测试会一直绿着而线上已错。
2. **按最坏情况给 token 预算**（2000 而非 900）：代价是延迟上升，换来截断概率归零。
   短记录不受影响——预算是上限不是固定开销。
3. **失败不抛异常**：返回 `{ok:false, raw, issues}`。接口永远不 500，调用方永远拿得到能处理的东西。

## 还没做

- **有氧只有计数、没有趋势**：游泳课没有组次，`getExerciseTrend` 对它无意义；
  `countTraining` 已经能按 `muscle_focus` 数到它（2026-11 有氧 3 次），但「游得比以前快不快」还没入口。
- **只有 20 篇**：样本量够说明稳定性，不够说明分布外泛化。213 篇力量记录里还有 193 篇没进过评测。
- **检索对 query 措辞敏感**：`w6:debug` 可以复现——同一个意图换个说法，top5 会变。
  现在靠「清洗掉时间副词/疑问词 + 时间重排」压住了已知的几类，但没有查询改写的通用机制。
- **命中子块会丢父节上下文**：问「练胸为什么脖子酸」时命中的是「明天怎么办」那个子节，
  模型把「怎么办」当「为什么」答了。下一步要在 prompt 里标注「[1] 是某节的子节」。

  3. ~~数值入口工具化~~ **已完成**（W7）：趋势 + 计数两个工具，都返回已算好的字段与 `caliber`，

  4. **流式 + 取消**（下一步）：现在同步非流式，热态 4–8 s 全程白屏。流式不解决首字，
     解决的是「看不出它在动」；取消解决的是「问错了只能等它说完」。
  5. **引用角标已做**（`[n]` 可点、跳转引用卡片）；还差**命中子块时标出它属于哪一节**，
     否则「明天怎么办」会被当成「为什么」答。

- **W5 留下的三件实验**（都还没做，按能改变结论排序，详见报告第 10 节）：
  1. **论述性语料进库**：现在只测了「每日记录」，计划文档、知识笔记、复盘都没进。
     那些才是向量该赢的地方，结论的适用范围被语料限死了。
  2. **补 10 道真·跨术语题**：现在只有 1 道，不足以下「向量在术语不一致时更好」这个判断。
  3. **混合检索 / 小块合并 / 人工相关性分级**：RRF 融合、合并短块、把二值判据换成 0/1/2。
- **两条口径债**（都是真实数据就这样，不是 bug，但**不能用错**）：
  - **`capacity` 字段含热身组**：11-07 = 40kg×8 热身(320) + 工作 1740 = 2060。
    拿它比「这周练得比上周多不多」会把多插热身的课算成进步——剔除热身可能结论相反
    （实测含热身 +4.9%、剔除 −12.8%）。报趋势必须同时报两个口径。
  - **容量不可跨动作求和**：1214 个动作里 41 个对不上，其中 34 个是引体——练练对自重按体重折算、
    对双侧算两侧。同动作内可比，跨动作不能加总。

- **硬切点不会切在句中**：40 个超长块（21 个续块）都按行累加后切，切点必然落在行首，不是滑窗那种半个句子——
  所以 `maxChars=1200` 暂不调整。真正的问题在别处：续块与首块共用同一个 `headingPath`，
  检索命中续块时看不出它是后半段。**这一点 W5 没有专门验证**（45 个续块里没有一道题打中它们），仍是待办。
